### A2. 标题与摘要

**标题模式**：动名词 + 规模限定词 + 任务名词短语（"Automating / Large-Scale / Data Quality Verification"），5 个词，无冒号、无系统名、无营销词。标题即贡献的动作。

**摘要逐句 move 标注**（共 8 句，**全句无一个数字**）：

| # | Move | 中文转述 |
|---|---|---|
| S1 | Context | 现代组织的每个业务流程与决策都依赖数据。 |
| S2 | Problem | 缺失或错误的信息会严重损害下游决策。 |
| S3 | Problem→Gap（隐含） | 因此校验数据质量很关键，但对所有参与者都很繁琐（暗示需要自动化；没有点名已有方法的不足）。 |
| S4 | Approach + Deployment 声称 | 提出一个规模化自动校验数据质量的系统，满足生产场景需求。 |
| S5 | Approach（机制 1） | 声明式 API 把常见约束与用户自定义校验代码结合，实现数据的"单元测试"。 |
| S6 | Approach（机制 2） | 把约束校验负载翻译成 Spark 上的聚合查询来高效执行。 |
| S7 | Approach（机制 3、4） | 支持对增长数据集的增量校验，并用 ML 做约束建议、列可预测性估计与历史质量时间序列的异常检测。 |
| S8 | Result（仅路线图） | 讨论设计决策、系统架构，并在多个数据集上做实验评估（未给出任何结果）。 |

观察：Approach 占 4/8 句，每句点名一个具体机制；Result 只有"我们做了评估"而无数字——这是 2018 年工业稿的常见写法，按今天的审稿标准偏弱。

### A5. 实验/评估

- **评估问题**（§5 引言隐含给出，未编号为 RQ）：Q1 批量指标计算是否随数据线性扩展？Q2 可预测性估计是否准确、训练是否够快？Q3 增量计算何时优于批量？Q4 自动建议的约束在留出数据上是否成立？Q5 异常检测能否发现有意义的问题（演示性质）？
- **数据集**：内部商品目录样本（约 1.2 亿条/50GB，专有）；reddit 评论（公开，Kaggle，取 5 万条）；twitter 用户 5,180 个（采样流）。专有 + 公开混合。
- **基线**：**没有外部系统基线**。只有内部对照：批量 vs 增量（§5.2）、启发式 vs 启发式+分类器（§5.3）、不同输入列组合与样本规模（§5.1）。
- **指标**：运行时间（秒）、加权 F1、约束覆盖率、分类器概率、AUC（在 §4.2 而非 §5 报告）。
- **结果呈现**：图 + 叙述，每个趋势都配"为什么"（线性因为是聚合查询；增量恒定因为只依赖增量大小；product id 增量更差因为直方图等于整列）。
- **局限的报告方式**：分散在出现处——append-only 假设（§3.2）、human-in-the-loop（§3.3）、增量开销与 product id 反例（§5.2）、错误建议与假阴性（§5.3）、不做修复（§7）。无单独 Limitations 节。无重复实验/方差/误差棒。
- **生产证据 vs 受控实验**：实验全部是受控的（采样数据、自建集群、异常检测为虚构用例）；生产证据只有摘要"满足生产需求"的声称与 §6 的定性经验，**没有采用规模或事故数字**。
