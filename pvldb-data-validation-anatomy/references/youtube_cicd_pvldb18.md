|---|---|---|

| S2 | Problem/Gap（原因清单） | 分布式归属、复制生产环境成本高、业务逻辑快速演化，导致管道脆弱、故障代价大。 |
| S3 | Approach + **Result** + Deployment | 提出新 CI 框架，在 YouTube 数仓实现 94.5% 的上线前问题检出，并大幅降低资源消耗。 |
| S4 | Approach（机制 1） | 核心创新：以生产配置驱动的测试方法，在生产环境内做可扩展、隔离的测试。 |
| S5 | Result（定性） | 该方法降低测试开销并保证高保真。 |
| S6 | Approach（机制 2） | 基于代数依赖模型的血缘感知影响分析，自动把数据质量检查传播到各组件，促进一致性与跨团队协作。 |

### B5. 实验/评估

- **评估问题**：未声明。可推断的隐含问题——框架能否降低测试数据量/时间（案例 1）、能否加快问题诊断（案例 2）、能否加速 schema 变更（案例 3）。

### 7.2 工业/系统型稿件 vs 研究轨道稿件的结构差异

以下"研究轨道"一列是 PVLDB 研究轨道的**一般惯例**（来自领域常识，不是这两篇论文的证据）；"工业/系统型"一列以本两篇为证据。

| 环节 | 研究轨道一般惯例 | 工业/系统型（本两篇所见） |
|---|---|---|
| Intro 的 gap | 点名已有方法的具体缺陷（技术性 gap），常有动机例子 + 贡献列表 + 结果摘要 | 以业务/组织痛点为 gap（A 的繁琐重复，B 的多团队与环境成本），很少点名已有方法 |
| 问题定义 | 独立的 Problem Definition / Preliminaries，含形式化定义 | 用"质量维度"（A §2）或"挑战清单"（B §2）代替形式化问题 |
| 技术核心 | 算法框、复杂度分析、定理/证明 | 架构图 + 组件说明 + 实现取舍（A 有半形式化的增量模型，B 没有） |
| 实现 | 常并入方法或实验设置 | 独立 Implementation 节，写清技术栈与存储（A §4） |
| 评估 | 编号 RQ、多个外部基线、公开数据集、参数敏感性、消融 | 扩展性曲线 + 内部对照（A）；或部署案例与前后对比（B）；外部基线普遍缺失 |
| 特有章节 | 少见 | "Learnings / Experience / Guiding Principles"（A §6 约 3%；B §3.4–3.5 约 22%） |
| 可复现性 | 越来越要求代码/数据工件 | 依赖专有数据与内部基础设施；A 用部分公开数据集补偿 |

结论：Paper A 是"读起来像研究稿的工业稿"——保留了工业稿的生产背景与经验节，但方法有模型、实验有图有负面结果，**适合作为骨架模板**；Paper B 是"经验报告型"工业稿，可借鉴其摘要量化、生产规模交代、前后对比案例的写法，但其证据可追溯性与引用密度**应作为反面检查项**。若目标是研究轨道，应采用 A 的骨架，再补上外部基线、编号 RQ 和形式化问题定义。

### 7.3 可检查规则（20 条，附证据位置）

每条格式：**规则** — 怎么查 — 证据（正例 ✔ / 反例 ✘）。

1. **贡献–节号–证据闭环**：每条贡献括注所在节，且至少对应一个量化结果。— 逐条把贡献映射到实验图/表编号。— ✔ A p2（1782）贡献列表均带节号，§5.1–5.4 一一对应；✘ B p1–p2（4887–4888）贡献无节号，"提交前测试"一条在正文只在 §3.3.1 一笔带过、无测量。
2. **总数字可追溯**：摘要/结论中的每个数字必须在正文出现，并给出定义（分子、分母、时间窗、样本量）。— grep 每个数字，检查正文是否有定义段落。— ✘ B 的 94.5% 只在摘要（p1）和结论（p8），10,000 倍只在结论（p8），且两处口径不一（"上线前检出" vs "阻止生产问题"）。
3. **摘要 move 完整**：Context → Problem → Approach（≥2 个具体机制）→ 带数字的 Result → 部署/适用范围。— 逐句标注 move。— ✔ B 摘要 S3 带数字与部署场景；✔ A 摘要 S5–S7 点名 4 个机制；✘ A 摘要 0 个数字，S8 只说"做了评估"。
4. **一个例子贯穿全文**：Intro 引入的具体场景要在方法、实现、实验中被回指。— 搜索例子关键词在各节出现次数。— ✔ A 视频日志例子出现在 Intro P2（p1）、§3.1 P2–P5（p2–p4）、§4 P2 回指（p7）；✘ B Intro P2 的场景之后未再出现。
5. **代码/配置清单逐行讲解**：清单要有行号，正文按行号讲。— 检查正文是否出现"第 x–y 行"式指称。— ✔ A Listing 1（p3）在 §3.1 按 1–2、7–9、10–11、12、13–14、16–19、21–24 行讲解。
6. **核心技术至少半形式化，假设显式**：给符号、模型和关键公式，并在模型处写明前提假设。— 检查核心节是否有 notation 段与 "we assume/restrict" 句。— ✔ A §3.2（p5–p6）计算模型 + append-only 限定 + 7 个展示公式；✘ B 的代数依赖模型只有 Table 2 两个例子，无定义。
7. **设计与实现分节**：方法讲"是什么/为什么"，实现讲技术栈、存储、物理执行和优化。— 检查是否存在独立 Implementation 节及其内容。— ✔ A §3 vs §4（p7–p9：Spark、DynamoDB、S3、Analyzer、扫描共享）；✘ B 把概览、能力、经验都堆在 §3。
8. **实验节开头三件套**：路线图 + 数据集（规模、来源、是否公开）+ 软硬件版本。— 检查实验节前三段。— ✔ A §5 P1–P3（p9）：1.2 亿条/50GB、reddit、twitter、EMR 5×c3.4xlarge、Spark 2.0.2；✘ B 无。
9. **每个实验子节五步**：目标句 → 设置 → 图表 → 观察到的趋势 → 为什么会这样。— 检查每个结果段是否有"因为"类解释。— ✔ A §5.1 P2（线性因为生成的是聚合查询）、§5.2 P2（增量恒定因为只依赖增量大小）。
10. **报告负面结果并解释**：至少给出一个方法不占优或出错的情形及原因/缓解。— 检查实验节是否有失败案例。— ✔ A §5.2（p10）product id 上增量始终更差；§5.3（p10–p11）两条错误建议 + 分类器纠正 + 假阴性；✘ B 无任何失败或局限。
11. **每个改进声称都有对照组**：至少有内部消融；研究轨道还需外部基线。— 列出所有"更快/更好"声称及其比较对象。— ✔ A 批量 vs 增量、启发式 vs 启发式+分类器；✘ A、B 都没有外部系统基线；✘ B 的前后对比未说明"前"如何测得。
12. **案例研究结构化**：每个案例写明对象规模、指标定义、前→后数值、观察窗口、样本数。— 检查每个案例这五个字段。— 半 ✔ B §3.4.1–3.4.3（p6–p7）有规模（100+ 组件）和前后数值（1 天→4 小时），✘ 缺窗口、样本数、测量方法；"若干问题"属模糊量词。
13. **数据图用结论式标题，表格可把协议写进标题**。— 检查每个数据图标题是否陈述趋势/结论。— ✔ A Fig.4（p9 "线性增长"）、Fig.9（p12 异常提示钓鱼）；✔ A Table 3（p11）标题含 10%/90% 协议；✘ B Fig.1 的颜色图例写在正文而非标题。
14. **交叉引用与表格指称一致**：每个节号/表行/图号引用都指向真实存在的对象。— 编译后检查所有 "Section x"、"row n"。— ✘ B §3.3.1（p5）引用不存在的 "Section 4.1.2"（应为 3.1.2）；✘ B §3.1.2（p4）称"第二行/第三行"，表中只有 2 个数据行。
15. **相关工作按主题组织，每个主题以技术对比句收尾**。— 检查每个 RW 主题段是否有"与本文不同在于（某技术属性）"的句子。— 半 ✔ A §7（p12）3 个 run-in 主题，仅第一个有对比句；✘ B §4（p8）单段罗列，以"更整体、更易用"等泛化词收尾。
16. **方法节引用所借用的构件**：用了什么算法/系统就在用处引用。— 方法节引用数 ≥ 借用技术数。— ✔ A §3–§4 引用 HLL [21]、分位数 [15]、Spark [50]、朴素贝叶斯 [36] 等，两节共 17 处引用；✘ B §3 约 3,850 词仅 2 处引用（且均为同公司系统），分层抽样、异常检测、配置重写均无出处。
17. **文献新近度与同题工作覆盖**：近 3–5 年文献占比不低于约 40%，同问题空间的代表系统必须引用并对比。— 统计年份分布；检索同主题系统是否被引。— ✔ A 66% 出自 2015–2018（即投稿当年及前 3 年）；✘ B 近 5 年 42% 尚可，但未引用同主题的数据质量校验系统（如 Paper A），且 4/19 条集中于同一作者组的小型会议论文。
18. **局限与假设写在出现处，未来工作具体可执行**。— 检查方法/实验中的 "we restrict / does not support" 句，以及结论里未来工作的条数与具体度。— ✔ A §3.2 append-only、§3.3 human-in-the-loop、§7 不做修复、§8 P2 列 5 条具体方向；✘ B 无局限，未来工作 3 条较笼统。
19. **经验/原则节短而有据**：每条经验对应一个观察到的事件或数字，篇幅控制在正文约 3–8%。— 检查经验条目是否回指具体案例/数据。— ✔ A §6（p11–p12）约 300 词、3%（但无数字）；✘ B §3.5（p7–p8）约 720 词、12%，内容为通用最佳实践（IaC、包管理器等），与本文证据无对应。
20. **克制用词**：不带数字的最高级/新颖性形容词应删除或配上证据。— grep "novel / unprecedented / unparalleled / significantly"，检查同句是否有数字或引用。— ✔ A "novel" 0 次；✘ B "novel" 8 次，"unprecedented"（§3.3.2）、"unparalleled"（§3.4.4）均无数据支撑。
