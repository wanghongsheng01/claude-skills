## 0. 为什么选它作第 4 篇范文

候选有两篇：Scorpion（PVLDB 6, 2013）与 Abedjan et al.《Detecting Data Errors: Where are we and what needs to be done?》（PVLDB 9, 2016, `vol9/p993-abedjan.pdf`）。选 Scorpion，理由：

1. **研究型形态完整**：形式化问题（Influential Predicates，IP 问题）→ 性质（incrementally removable / independent / anti-monotonic）→ 利用性质的算法（DT、MC）与剪枝正确性论证 → 带人工构造 ground truth 的合成实验 + 两个真实数据集。这正是"形式化保证 + 算法 + 数据管道中的错误定位/解释 + 强实验"的形状。
2. **与"由聚合语义派生检查"的问题直接同构**：它把 SUM/COUNT/AVG 的可减性（`SUM(D−s)=SUM(D)−SUM(s)`）当作一等公民的算法性质，并按聚合函数的代数性质分派算法，这是派生守恒/对账类检查的论文最需要借鉴的写法。
3. **成本—质量的权衡写法**：与穷举算法比质量（F-score），比代价（运行时间，对数轴），并用一个可调旋钮 c 展示整条权衡曲线。
4. Abedjan 是对已有工具的实验性分析（无新算法、无形式化保证），更接近 EA&B 形态，与本 skill 的目标稿件形态不符，故不采用。

不足（不要照搬）：年代较早（2013），文献只有 19 条、偏旧；没有定理与证明；唯一对照是自己实现的穷举算法；真实数据集只有定性展示；结果图图注为描述式。

## 2. 标题解剖

`Scorpion: Explaining Away Outliers in Aggregate Queries`（7 词）

| 成分 | 功能 |
|---|---|
| `Scorpion:` | 系统名，品牌化；全文一直以名字指代系统 |
| `Explaining Away` | 动作动词 + 结果状态：不是"检测"异常，而是找到使异常"消失"的解释——标题直接写出了问题的操作性定义（删除谓词所选元组后异常不再异常） |
| `Outliers` | 对象：用户在可视化中标出的异常输出点 |
| `in Aggregate Queries` | 范围：只针对 group-by 聚合查询，这是后文所有代数性质成立的前提 |

模板：`<System>: <Verb-ing> <Away/Down> <Symptom> in <Query/Pipeline Class>`。标题里的范围词（aggregate queries）就是后文所有性质与算法的适用边界，题文一致。

观察：
1. **A5 是全文最重要的一句**：把一个模糊需求（"解释异常"）变成可检验的条件（删去谓词选中的元组后异常消失）。形式化（§3.2 的 ∆ 定义）就是这句话的符号版。
2. 结果句区分了证据类型：真实数据只说"能找到"，速度与质量的比较只在合成数据上声称——**声称的强度与证据的类型匹配**。
3. 没有具体数字（只有"orders of magnitude"）。2013 年可以接受；今天的 PVLDB 研究稿建议给出可追溯的数字（见 `fingerprints.md`）。

### §2 Motivation and Use Case（p2L–p2R，712 词）
- 2-P0 路标：先建运行例子，再讲若干用例。
- **Sensor Data（运行例子）**：Table 1 给 9 个元组（T1–T9：时间、传感器、电压、湿度、温度）；Q1 按小时求平均温度；Table 2 给 3 个结果及用户标注（α1 hold-out、α2/α3 outlier，误差向量 <−1>…）。**这两张小表是全文所有公式的数值实例来源**（§3.2 用 T4/T6 算出 −10.8 与 21.6）。随后列出分析师可能提的 4 个问题，并把它们映射到"影响程度"与"异常 vs 正常对比"两类需求——**需求清单直接预告了形式化的两个成分**（影响度、hold-out）。
- **Medical Cost Analysis**：与一家匿名医院合作；15% 的高成本患者占 50%+ 费用；人工挑维度排查才发现少数医生过量开处方。说明为什么"单独找昂贵治疗"不够（治疗之间可能无关）——**用真实用例证明"谓词形式的解释"这一输出形态的必要性**。
- **Election Campaign Expenses**：实验数据集之一，强调终端用户只能看预制图表。
- **Extending Provenance Functionality**：已有溯源系统对聚合结果会把大半数据都标为来源（技术上正确但无信息量），Scorpion 能把聚合溯源缩小到少量高影响输入。**把自己定位为已有溯源能力的增强，而不是替代**。

### §3 Problem Statement（p2R–p4L，1,626 词）
- 3-P0：一句目标 + 两个需要定义的东西（影响度、用户可提供的附加信息）+ 指向 Table 3 符号表。
- **3.1 Setup**：单关系 D、属性 A；group-by 属性 A_gb、聚合属性 A_agg、其余属性 A_rest（解释只能用 A_rest）；**join 查询通过物化 join 结果当作 D 来覆盖**（一句话处理范围扩展）。每引入一组符号，立刻用 Q1 实例化（A_gb={time}，A_agg={temp}，A_rest={SensorID, Voltage}）。定义谓词（连续属性的区间子句、离散属性的集合包含子句，每属性至多一个子句）、谓词包含关系 ≺_D、输入组 g_α、异常集 O、hold-out 集 H（H∩O=∅）、误差向量 v。
- **3.2 Predicate Influence**：**逐层构建定义**，每层一个 run-in 小标题：
  1. Basic Definition：来自敏感性分析（偏导 ∆y/∆x），∆_agg(o,p)=agg(g_o)−agg(g_o−p(g_o))，影响度 = ∆ / |p(g_o)|；立刻用 Table 1/2 数值演算（T4 影响 −10.8，T6 影响 21.6，所以 T6 最有影响，"这符合直觉，因为……"）。脚注说明其他形式化（扰动值而非删除）可行但不讨论——**主动声明未选的设计**。
  2. 解释为什么定义在谓词而不是元组上（谓词可跨多个输入组）。
  3. Error Vector：只取与误差方向一致的分量（点积）；正反两种方向各算一次例子。
  4. Hold-out Result：λ 加权，减去对 hold-out 影响的绝对值；解释为何用绝对值（任何扰动都惩罚）。
  5. Multiple Results：对异常取平均、对 hold-out 取最大；**一句话给出设计理由**（最大值对任何 hold-out 的影响设硬上限）。
  6. 简写约定 inf(p)、∆(p) 等。
- **3.3 Influential Predicates Problem**：给定查询与用户输入，求 argmax 影响度的谓词。随后一段"为什么这个问题难"：先抛出读者最自然的质疑（为什么不直接返回温度最高的读数？），然后列 4 个理由（元组组合的交互取决于聚合函数；必须返回谓词而非任意元组——top-k 包围盒的三个毛病；影响度依赖元组统计量而统计量因聚合而异；hold-out 使简单贪心失效）。**"预先回应最自然的简单解法"是本节的关键手法**。
- 形式化的放置：问题定义在 §3（第 3 页），性质在 §5，算法在 §6；没有定理环境。

### §4 Basic Architecture（p4L–p5L，832 词）
- 4-P0：本节给系统架构与"不假设任何聚合性质"的朴素实现，并说明它们为什么低效——**先给能处理任意 UDA 的通用但慢的版本，再在 §5–6 用性质加速**。
- **4.1 Architecture**（Fig 2）：端到端数据探索工具；Provenance → Partitioner → Merger → Scorer；Fig 3 三联图（元组影响热度 / Partitioner 输出 / Merger 输出）。点明代价瓶颈：Scorer 计算 ∆ 需要删除元组后重算聚合，并要对所有输入组做——并前指 §5.1 的性质如何降低此代价。
- **4.2 Naive Partitioner**：穷举所有单属性子句及其合取；给出复杂度论证（离散属性子句数随基数指数增长，连续属性二次增长，合取空间随属性数指数增长）。
- **4.3 Basic Merger**：最小包围盒/值并集合并，贪心扩张直到影响度不再增加；指出黑盒聚合下的性能问题并前指 §6.3。

### §5 Aggregate Properties（p5L–p6L，1,049 词）
- 5-P0：性质只需聚合开发者实现一次，对终端用户透明——**说明谁承担形式化的负担**。
- **5.1 Incrementally Removable**：先直观（SUM(D−s)=SUM(D)−SUM(s)，SUM(D) 可缓存），再形式化为 state/update/remove/recover 四函数分解；与 OLAP 的 distributive/algebraic 函数对比异同，并给反例（MAX、MIN、MEDIAN、MODE 不可减；COUNT/SUM 的算术组合如 AVG、STDDEV、VARIANCE 可减）；最后给 AVG 的四函数实例。**"直观 → 形式化 → 与已知概念的异同 → 正例/反例 → 具体实例"五步**。
- **5.2 Independent**：两条件的形式定义 + 逐条用一句话解释含义 + 推出贪心策略并声称可找到最优元组集合（非最优谓词）；随即承认这些条件难以保证，改为在 ∆ 上定义、由开发者声明标志位。
- **5.3 Anti-monotonic Influence**：定义（子谓词影响不超过父谓词，于是不影响的谓词可剪枝）；**明确写出成立前提**（如 SUM 要求非负数据），并给出 check(D) 函数让系统运行时判断前提是否满足。

### §6 IP Algorithms（p6L–p8R，2,402 词）
- 6-P0：性质使通用指数问题可用更高效的划分与合并算法求解；预告 DT（自顶向下，用于 independent）与 MC（自底向上，用于 independent + anti-monotonic）。**按聚合性质分派算法**。
- **6.1 DT**：6.1.1 递归划分——先讲经典回归树，再讲改动（关键洞见：含高影响元组的分区要精确，不含的可以放宽误差阈值），给出阈值函数及 Fig 4 曲线；6.1.2 采样——用"样本中以 ≥95% 概率包含高影响元组"推出采样率，再按影响分层采样；6.1.3 并行划分与同步——用 Table 2 的 α2/α3 说明合并输入组为何会过度划分；6.1.4 合并异常/hold-out 两套划分（Fig 5）。
- **6.2 MC**：先讲 CLIQUE 子空间聚类，再讲两处修改；Fig 6 给出影响度**不满足**反单调的两种情形（影响了 hold-out / 没影响异常），说明如何保守剪枝；伪代码 + 逐行讲解（"Lines 5–8 … Lines 9, 10 …"）；用 {1, 50, 100} 的 SUM 反例说明影响度（∆/|p|）本身不反单调，并给出使剪枝成立的条件。**先给反例，再给修正后的充分条件**——这是剪枝正确性论证的写法。
- **6.3 Merger 优化**：只扩张前四分位谓词；对可减聚合用缓存元组 + 四函数近似影响度，Fig 7 与按体积估计各分区贡献的公式；指出代价只依赖相交分区数而非数据规模。
- **6.4 降维**：与算法正交，可用特征选择；目前依赖用户指定，自动化留作未来工作。

### §7 An Additional Knob（p8R，252 词）
- 提出影响度的一般化：∆o / (∆g_o)^c，c ≥ 0 控制"结果改变量"与"谓词选中元组数"的权衡；c=0 时选很多元组，c 增大选更精确的谓词；算法无需修改；前指实验将系统研究 c。**把一个隐藏在定义里的设计选择显式化为用户旋钮，并让实验围绕它展开**。

### §8 Experiments（p8R–p12L，2,704 词，结果图 8 幅）
- **8-P0 目标段**：比较 NAIVE、DT、MC 的性能与答案质量，并理解 c 如何影响所生成谓词；先用维度与难度可控的合成数据，再"因篇幅所限"定性评述 4 维与 12 维的真实数据。**目标段写明问题、对照、数据与证据强度**。
- **8.1 Datasets**：
  - SYNTH：查询为 SUM group-by；10 组 × 每组 2,000 元组；正常值 N(10,10)，高值异常 N(µ,10)，中值异常 N((µ+10)/2,10)；异常组内两个嵌套超立方体（外层占组内 25%，内层占外层 25%）；5 组作 outlier、5 组作 hold-out；维度 2–4；难度 Easy µ=80、Hard µ=30。Fig 8 可视化 2D 例子。**ground truth 由构造给出，难度由一个参数连续控制**。
  - INTEL：230 万行、6 属性（4 个用于解释）；STDDEV 查询；两种故障（传感器 15 读数 >100°C：20 个 outlier / 13 个 hold-out；传感器电量低：138 / 21）。
  - EXPENSE：116,448 行、14 属性（12 个用于解释，基数 2 到 1.8 万）；SUM 查询；7 个 >$10M 的异常日、27 个正常日。
- **8.2 Setup**：指标为对照 ground truth 元组集的 precision / recall / F-score 与运行时间；**NAIVE 改造为 anytime 版本**（按复杂度递增枚举，最多跑 40 分钟、每 10 秒记录当前最优）——这是让指数级对照在有限时间内可比的公平化处理；Python 2.7、单线程、MacBook Pro 8GB；连续属性切 15 等份。
- **8.3.1 Naive Algorithm**（Fig 9–11）：Fig 9 展示不同 c 下 NAIVE 的最优谓词（c=0 包住外层立方体及许多正常点；c 增大只选内层）；**主动承认"不存在单一 ground truth"**，于是用内外两层立方体作为两个替代 ground truth；Fig 10 精确率/召回/F 随 c 变化并解释曲线形状；Fig 11 收敛时间，解释曲线为何不单调（影响度最优与所选 ground truth 不完全相关）。**Takeaway**（粗体 run-in）：F-score 是好的代理但可能因 c 被人为压低；NAIVE 在 c 很低时收敛快、c 高时很慢。
- **8.3.2 Comparing Algorithms**（Fig 12–15）：Fig 12 三算法质量随 c 变化（最大 F 相近）；Fig 13 随维度变化（DT、MC 与 NAIVE 相当，DT 有时更好，并给两条原因：DT 可任意细分粒度、NAIVE 在高维 40 分钟内跑不完）；Fig 14 代价随维度（快约两个数量级；MC 的代价随 c 增大而增大，因为可剪枝机会变少——**主动报告自家算法的不利趋势及机制**）；Fig 15 代价随数据规模（5k→100k 元组线性，斜率随维度超线性增长）；**负结果**：DT 在不含高影响元组的分区上浪费大量划分时间，降低噪声重跑后快 2×，更高级优化留作未来工作。**Takeaway**：DT、MC 与穷举质量相当、代价最多降 150×；性能依赖数据性质，最坏情况随维度指数增长；DT 的 F 可能高于 NAIVE。
- **Caching Optimization**（Fig 16）：DT 划分与 c 无关，可缓存；Merger 可从更大 c 的结果续算；结果：低 c 时缓存收益最大，高 c 时几乎无收益并解释原因。**Takeaway**：低 c 下最多降 25×。
- **8.4 Real-World Datasets**：没有 ground truth，所以展示生成的谓词并对照预期与进一步分析评述质量；所有算法几秒完成，因此只谈质量。INTEL 两个工作负载都找到了故障传感器（15、18），并在 c 接近 1 时给出更细的子谓词（电压/光照区间），作者解释其物理含义；EXPENSE 把 >$1.5M 的支出定义为 ground truth，F-score 0.6（召回低），但论证该谓词是最好的描述（某媒体采购商的某份报告，均值 $2.7M）。**真实数据上声称的强度降为"定性 + 可解释"，并诚实报告低 F 值**。

胜/平/负的表述：
- 对唯一对照 NAIVE：质量"comparable"（相当），个别情形 DT 更好并解释原因；代价"up to two orders of magnitude / 150×"。没有声称全面胜出。
- 负结果 3 处：MC 代价随 c 增大；DT 在非影响分区浪费时间；EXPENSE 召回低。每处都配机制解释。
- 没有误差棒或重复实验；单机单线程。

### §9 Related Work（p12L，448 词，放在最后）
- 5 段，按主题：① 溯源中的影响度（Meliou 等，最接近，放第一段）；② 概率溯源的影响度——**段末对比句**：这些工作能给元组排序，但不构造解释性谓词；③ OLAP 解释（iDiff、发现驱动的立方体探索、RELAX）——**段末对比句**：Scorpion 显式以影响度为优化目标，并支持 hold-out 与误差向量；④ MRI、PerfXplain——对 PerfXplain 给对比句（它标注作业对，Scorpion 标注聚合结果并需推断输入标签）；⑤ HCI 视角（Profiler、众包解释）——无对比句。
- 一句话定位：已有影响度只给元组排序，已有 OLAP 解释不以影响度为目标、不支持 hold-out；Scorpion 以影响度为目标、输出谓词。

### §10 Conclusion（p12L–R，198 词，1 段）
- 趋势 → 系统做什么 → 影响度概念 → 难点（影响依赖组内其他元组）→ 三种性质 → 质量几乎相同、快若干数量级 → 两个真实数据集结果"promising"。**无数字、无局限、无未来工作**（未来工作散在 §6.4 与 §8.3.2）。

## 6. 形式化与算法呈现（专项）

| 维度 | Scorpion 的做法 | 可借鉴点 |
|---|---|---|
| 定义的引入顺序 | 运行例子（§2 Table 1/2、Q1）→ 符号（§3.1，每个符号立刻实例化）→ 逐层定义（basic → 误差向量 → hold-out → 多结果）→ 每层一个数值演算 | 逐层加约束、每层配例子，读者始终能手算 |
| 设计理由 | 每个定义选择配一句"为什么"（谓词而非元组；绝对值；最大值作硬上限；删除而非扰动在脚注中声明） | 每个形式选择都要有一句理由或一句"另一种选择及为何不选" |
